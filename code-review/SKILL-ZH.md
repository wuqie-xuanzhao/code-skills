# 代码审查

## 概述

Code review 是一道安全网——在 bug 上线之前捕获它们，同时提升团队的整体代码质量。但一次好的 review 不仅仅是"找 bug"：它验证意图、检查假设，并记录推理过程，让下一个读者理解代码*为什么*是正确的。

本技能产出结构化的审查报告。默认在对话中直接呈现，只有用户明确要求保存/归档时才写入文件（`docs/superpowers/reviews/`）。

本技能只负责审查"代码做了什么、是否正确"。用户意图不同时（探索架构 → `code-explore`、修 bug → debugging 技能、规划改动 → writing-plans 技能），让用户选对应技能。

## 何时使用

**应该使用：**

- 合并 PR 或功能分支之前
- 实现完功能或修完 bug 后——声称完成前先验证
- 用户问"这段代码好不好？"或"帮我 review 一下"
- 对模块或子系统做定期质量审计
- 入职时：review 一个模块以建立质量基线

**不适用：**

- 用户想探索架构但不做评判 → 用 `code-explore`
- 用户已经知道 bug 是什么、想修它 → 用 debugging 技能
- 用户想规划新功能 → 用 writing-plans 技能
- 用户想重构 → 用 refactor 技能

## 三种审查类型

| 类型 | 适用情境 |
| --- | --- |
| **quick** | 小改动（&lt; 200 行）、单文件或紧凑范围、低风险 |
| **standard** | 功能级改动、多文件、中等复杂度 |
| **deep** | 关键路径改动、安全敏感、大型重构或发布前 |

各类型的产出差异：

- `quick`：摘要 + 发现表即可；除非有严重发现需要解释，不写详细章节
- `standard`：摘要 + 发现表 + 详细发现 + 值得肯定的点
- `deep`：完整报告，包括跨文件分析、安全章节、流程改进建议

## 工作流

### Phase 1：范围与上下文

明确审查目标和原因：

1. **确定目标** — diff、分支、PR、指定文件或目录
2. **理解意图** — 读 PR 描述、commit message，或问用户："这次改动要达成什么？"
3. **建立基线** — 改之前的代码是什么样的？存在哪些不变量？

最多问两个问题：

1. "这次改动的主要目标是什么？"
2. "有没有你特别担心的地方？"

用户描述已清楚时直接进 Phase 2。

### Phase 2：阅读代码

#### 阅读策略

按以下顺序阅读：

1. **Diff 优先** — 理解改了什么、为什么改
2. **被改函数的完整上下文** — 未改动行中的 bug 也在审查范围内
3. **调用者和被调用者** — 改动是否破坏或假设了某些调用方式？
4. **测试** — 现有测试是否覆盖了被改行为？需要新测试吗？

#### 工具选择优先级

1. **Diff / git 工具** — 看改了什么，而不是存在什么
2. **代码图谱/索引** — 追踪调用者、被调用者和影响范围
3. **读源码** — 用实际代码确认可疑模式
4. **Grep / Glob** — 在代码库中搜索模式

> 大多数编码 Agent 都提供等价工具——用你手头的即可。重要的是工具类别，不是工具名：
>
> | 类别 | Claude Code | Cursor | Cline | Aider | omp | Codex |
> |------|-------------|--------|-------|-------|-----|-------|
> | 1. Diff / git | `Bash`（git diff） | `@terminal` / 运行 git diff | `execute_command` | `/diff` | `bash` + `read pr://` | `shell`（git diff） |
> | 2. 代码图谱/索引 | codegraph MCP | `@codebase` | `search_files` | repo map（自动） | `lsp` + `ast_grep` | `shell`（ctags/grep） |
> | 3. 读源码 | `Read` | 打开文件 / `@file` | `read_file` | `/add` | `read` | `read_file` |
> | 4. 搜索 | `Grep` / `Glob` | Find in files | `search_files` | `/search` | `search` + `find` | `shell`（grep/find） |

#### 影响范围映射

在深入阅读代码之前，先映射变更的"爆炸半径"。这对 AI 生成的代码尤其关键——局部正确可能掩盖全局破坏。

1. **列出每个受影响的模块/目录** — 不只是文件，而是它们所属的子系统
2. **识别导出接口** — 任何被其他模块引用的函数、类型或常量变更
3. **检查数据形态变化** — 数据库列、API 响应字段、配置键、环境变量
4. **追踪调用链** — 谁调用了被改的代码？谁依赖它的输出？

写一段简短的影响范围说明（3–5 行）。这段说明会成为报告的"审查范围"章节，指导后续深入审查的方向。

为什么重要：AI 生成的代码通常在局部看起来正确，但会破坏隐藏约束——一个内部辅助函数的行为变更会波及 15 个调用者，或者返回类型变化会破坏下游一个没人记得的序列化器。先映射范围可以避免视野狭隘。

### Phase 3：多维度审查

运行以下审查角度。每个角度独立发现——不要用一个角度的结论压制另一个角度。

#### 角度 1：正确性

对每一行改动，问：什么输入、状态、时序或平台会让这行出错？

- 条件反转 / 错误条件、off-by-one
- Null / undefined 解引用
- 缺少 `await`、未处理的 promise
- 变量名复制粘贴错误
- catch 块吞掉错误
- 边界情况：空输入、最大值、并发访问

#### 角度 2：被移除的行为

对每一行被删除或替换的代码，说出它保护的**不变量**。搜索新代码：这个不变量还在吗？不在就是一条发现。

- 被移除的守卫或校验
- 被丢弃的错误处理路径
- 被收窄的类型约束
- 被删除的测试（且该测试覆盖的是真实场景）

#### 角度 3：跨文件影响

对每个被改动的函数，检查调用者和被调用者：

- 新的前置条件——现有调用者是否满足？
- 返回值形状变化——消费者是否兼容？
- 新抛出的异常——上游是否捕获？
- 新引入的时序 / 顺序依赖

#### 角度 4：语言与框架陷阱

扫描当前语言/框架的经典陷阱：

- JS：falsy-zero、`==` 隐式转换、闭包捕获循环变量、浮点数相等
- Python：可变默认参数、延迟绑定闭包、`is` vs `==`
- Go：nil-map 写入、range 变量捕获、goroutine 泄漏
- SQL：注入、缺少参数化
- 通用：时区/夏令时漂移、竞态条件、资源泄漏

#### 角度 5：质量与可维护性

标记让代码更难理解、修改或测试的问题：

- 重新实现了已有工具函数——应该调用已有的
- 不必要的复杂度：可推导的状态、深层嵌套、死代码
- 复制粘贴后微调——应提取公共逻辑
- 缺少或误导性的注释
- 命名不当导致意图模糊

#### 角度 6：安全性（适用时）

仅当改动涉及以下内容时触发：认证、输入处理、数据存储、网络通信或配置。

- 输入校验缺口
- 认证/授权绕过
- 敏感数据暴露
- 注入攻击面
- 不安全的默认值

#### 角度 7：回归验证

这个角度区分"新代码能用"和"旧功能没坏"。对于 AI 生成的改动，这是最关键的角度——AI 能满足即时需求，同时静默地破坏已有行为。

系统性执行以下检查：

**a) 测试执行与缺口**

- 运行已有测试套件。报告：通过 / 失败 / 跳过 的数量
- 如有测试失败，调查：是本次改动导致的，还是本来就已失败？
- 识别缺少测试覆盖的变更行为——每条都是一个回归风险
- Bugfix PR：是否有复现原始 bug 的测试？如果没有，审查前先补一个

**b) 接口与契约兼容性**

- 函数签名变更 → 所有调用方是否仍能编译 / 正常工作？
- 返回类型或结构变更 → 消费方是否正确处理新结构？
- 错误码或异常类型变更 → 上游 catch 块是否仍然正确？
- 新增必需参数 → 已有调用点是否提供了该参数？
- API 端点变更 → 检查路径、方法、请求头、请求体的破坏性变更

**c) 数据兼容性**

- 数据库 schema 变更 → 迁移是否可逆？历史数据是否仍可用？
- 配置键或环境变量变更 → 已有部署是否会中断？
- 文件格式或序列化变更 → 旧数据是否仍可读取？

**d) 性能回归**

- 热路径中新增循环 → N+1 查询、原本 O(n) 变成 O(n²)
- 移除了缓存或记忆化
- 更大的负载或响应体
- 异步上下文中新增阻塞调用

**e) 行为副作用**

- 改动是否改变了日志、指标或可观测性？（隐性回归：监控不再捕获问题）
- 改动是否修改了其他代码隐式依赖的默认行为？
- 改动是否引入了新的顺序或时序依赖？

每条回归风险记录为一条发现，严重程度为 `major`（可能破坏生产环境）或 `minor`（潜在风险）。已验证为安全的风险（测试通过、手动检查完成）放入"验证清单"章节，不作为发现。

### Phase 4：分类与优先级

按严重程度分类每条发现：

| 严重程度 | 含义 | 需要的行动 |
| --- | --- | --- |
| **critical** | 会导致生产环境 bug、崩溃或安全问题 | 合并前必须修复 |
| **major** | 真实条件下很可能出问题；边界情况已被破坏 | 合并前应该修复 |
| **minor** | 代码异味、次优模式或可维护性问题 | 方便时修复 |
| **suggestion** | 风格偏好、命名改进或可选优化 | 考虑采纳，不阻塞 |

**规则：**

- 两个等级之间拿不准时，往**高**了分（宁可信其有）
- 每条发现**必须**包含 `file:line` 证据
- 每条发现**必须**包含具体的故障场景（什么输入/状态触发问题）
- 没有 `file:line` 的建议可以存在，但必须标注为主观意见

### Phase 5：撰写报告

- **摘要先行** — 2–3 句话：审查了什么、整体评估、关键风险
- **发现表** — 所有发现按严重程度排序
- **详细发现** — 每条发现一个子节，含证据和修复建议
- **回归风险** — 列出可能被本次改动破坏的已有行为、接口或数据；每条标注已验证或未验证
- **验证清单** — 检查了什么：测试运行结果、手动验证完成情况、剩余缺口
- **值得肯定** — 标注好的模式、巧妙的解决方案、结构清晰的代码
- **建议** — 流程或架构层面的建议（不是个别修复建议）

起草完整报告。对照退出条件自检。

**语言与格式：**

- **语言：** 报告必须使用用户正在使用的语言撰写。用户说中文就写中文，说英文就写英文。全文——包括标题、发现、证据和建议——都跟随用户的语言。
- **格式：** 默认 Markdown（`.md`）。用户也可以选择 HTML 格式（`.html`）。选择 HTML 时：
  - 使用精致的专业样式表——不是简单的 Markdown 转 HTML。HTML 产出的视觉呈现应与 Markdown 源文件有明显区别：更丰富的排版、有意义的配色和清晰的视觉层次。
  - 利用 HTML 独有能力：可折叠的 `<details>` 展开详细发现、颜色编码的严重程度标签（🔴 critical、🟠 major、🟡 minor、🔵 suggestion）、浮动目录、样式化提示框区分关键发现与次要说明、带语法高亮和行号锚点的代码块。
  - 保持与 Markdown 模板相同的章节结构——HTML 是展现层，不是重构层。
  - 内嵌 `<style>` CSS，使文档自包含、可移植。

### Phase 6：交付与迭代

- 向用户呈现报告
- 讨论用户不同意的发现——解释推理，但在领域特定的权衡上接受用户的判断
- 讨论中出现新信息时修订报告
- 只有用户明确要求时才归档到 `docs/superpowers/reviews/`

## 反模式

| 反模式 | 为什么是错的 |
| --- | --- |
| 不读 diff 就开始 review | 只看新代码会遗漏被移除的行为 |
| 发现不带 `file:line` | 读者无法验证或定位问题 |
| 只找 bug | 忽略质量和可维护性问题会导致技术债 |
| 纠结格式胜过实质 | 格式偏好浪费 review 时间；先关注正确性 |
| 没有正面反馈 | 让人沮丧；好的模式值得被认可 |
| 审查自己写的代码 | 确认偏误会让你看不到自己的错误 |
| 模糊的发现（"这不好"） | 每条发现必须解释为什么以及怎么修 |
| 忽略测试覆盖率 | 没测试的代码就是没验证的代码——要标记 |

## 退出条件

在标记审查完成之前：

- \[ \] 审查范围和意图已明确
- \[ \] 影响范围已映射：受影响模块、接口、数据结构已识别
- \[ \] 所有改动文件及其所属函数已阅读
- \[ \] 跨文件影响已分析（调用者/被调用者）
- \[ \] 已有测试套件已运行；失败项已调查
- \[ \] 回归风险已识别并标注（已验证 / 未验证）
- \[ \] 每条发现有 `file:line` 证据和具体故障场景
- \[ \] 发现已按严重程度分类
- \[ \] 报告包含摘要、发现、回归风险、验证清单、值得肯定和建议
- \[ \] Frontmatter 包含 `commit`（审查时的 VCS 哈希）
- \[ \] 严重和重要发现有明确的修复建议
- \[ \] 报告已交付并与用户讨论

## 最终规则

```
先读 diff —— 审查改了什么，而不只是存在什么
每条发现需要证据 —— file:line，否则不算数
严重程度要诚实 —— 不要为了回避冲突而降级
抓 bug 优先于格式 —— 正确性永远高于格式
不当橡皮图章 —— 如果没什么可说的，说说为什么好
```

没有你的人类伙伴的许可，没有例外。
