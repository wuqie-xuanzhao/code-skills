KCP Reliable Transport Protocol

Type: module-overview Status: active Scope: 8 files across 4 dirs
01. Quick Answer
Conclusion first: KCP is an optional reliable transport layer that QmClient overlays on top of DDNet's native UDP. The client has zero configuration — it follows the server automatically.

Core architecture:

[Game Protocol CNetConnection/CNetChunk] → [CNetKcpSession/ikcp] → [UDP Socket]

Negotiation: server SERVERCAPFLAG_KCP → client NETMSG_KCP_CAPABLE → server NETMSG_KCP_ACCEPT + conv → both activate.

┌─ Negotiation ──────────────────────────────────────┐ │ Server ──SERVERCAPFLAG_KCP──▶ Client │ │ Client ──NETMSG_KCP_CAPABLE─▶ Server │ │ Server ──NETMSG_KCP_ACCEPT──▶ Client (+ conv ID) │ └────────────────────────────────────────────────────┘ ┌─ Transport ────────────────────────────────────────┐ │ VITAL packets ──▶ CNetKcpSession ──▶ UDP │ │ Non-VITAL ──────▶ Legacy UDP bypass ──▶ UDP │ └────────────────────────────────────────────────────┘

03. Details
Hybrid Transport Design

Not all packets need reliable transport. Player input snapshots (high-frequency, latency-sensitive) use the UDP bypass, while game state synchronization uses KCP.

Why KCP Over TCP

KCP trades ~10% extra bandwidth for 30–40% lower average RTT, and doesn't suffer TCP head-of-line blocking.
