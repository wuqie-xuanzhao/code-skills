# 代码探索

## 概述

同一个问题第一次花两小时查代码，第二次应该五分钟内找到答案——前提是第一次做完留下证据化的记录。

code-explore 把"提问 → 读代码 → 得结论"沉淀成可检索的探索文档，产出存放在 `docs/superpowers/explore/`。

本技能只负责"看到了什么"的证据化记录。用户意图是别的（拍板 / 处方 / 修 bug）让用户选对应技能。

## 何时使用

**应该使用：**
- 新人入仓快速理解模块边界 / 调用链 / 入口
- 用户提具体问题但暂时不要求产出方案或修复
- 功能设计或 bug 分析前先补一轮证据化探索
- 技术方向还在讨论，需要轻量 spike（只探索不拍板）

**不适用：**
- 用户已经知道要做什么、有明确实现方案 → 直接执行
- 用户要修 bug → 探索手段有助于定位，但目标是修复而非记录
- 用户要做新功能 → 探索手段有助于设计，但产出是 plan/spec 而非 explore 文档

## 三种探索类型

| 类型 | 适用情境 |
|------|----------|
| **question** | 围绕一个具体问题查代码并给结论 |
| **module-overview** | 快速梳理某模块结构 / 边界 / 入口 / 依赖 |
| **spike** | 对多个可能方向做轻量技术探查（不做最终决策） |

三种类型的产出格式差异：
- `question`：速答直接回答问题；关键证据是支撑答案的代码引用；一般不需要 Mermaid 图（除非涉及跨模块调用链才有帮助）
- `module-overview`：速答复 Mermaid 架构图；关键证据覆盖入口、核心流程和边界
- `spike`：速答含 Mermaid 多方案对比图；关键证据按方案分组；结论只说"可行/不可行/有风险"，不替用户选方案

## 工作流

### Phase 1：收敛探索问题

最多两个问题：

1. "你最想先回答的一个问题是什么？"
2. "希望聚焦哪个模块 / 目录？"

用户描述已清楚直接进 Phase 1.5。

### Phase 1.5：查重叠与意图分流

在 `docs/superpowers/explore/` 下匹配已有文档：

- 按文件名关键词匹配
- 按 frontmatter 字段匹配（`type`、`status`、`confidence`、`scope`）
- 按正文标题/内容关键词匹配

命中旧文档后判断本次意图：

- **新建**：无旧文档命中，或命中但已标记 `status: outdated` → 进 Phase 2 正常探索
- **更新**：旧文档仍在范围内，代码未大变，只补证据或修正局部结论 → 读旧文档 → 补证据 → 改回原文件，在 frontmatter 追加 `updated: YYYY-MM-DD`
- **替代**：旧文档核心结论已被代码变更推翻 → 旧文档标记 `status: outdated` + `superseded-by: <新文件名>` → 新建替代文档

触发词：用户说"再探一下"、"复查"、"更新上次那个 explore"、"上次探过的 X 现在变了没"。

### Phase 2：证据化探索

#### 工具选择优先级

探代码时按以下优先级选择手段：

1. **代码图谱/索引优先**——定位符号、追踪调用链。比文本搜索快一个数量级，且能追踪动态分派与回调。
2. **批量扫查次之**——大范围搜索多个目录/命名约定，收集概况而非返回全文。
3. **源码精读兜底**——关键证据必须读实际源文件以确认行号，避免索引缓存延迟导致行号偏差。
4. **文本搜索备用**——前两者都不可用时，用文件名匹配 + 内容正则展开探索。

> 大多数编码 Agent 都提供等价工具——用你手头的即可。重要的是工具类别，不是工具名：
>
> | 类别 | Claude Code | Cursor | Cline | Aider | omp | Codex |
> |------|-------------|--------|-------|-------|-----|-------|
> | 1. 代码图谱/索引 | codegraph MCP | `@codebase` | `search_files` | repo map（自动） | `lsp` + `ast_grep` | `shell`（ctags/grep） |
> | 2. 批量扫查 | Explore Agent | `@codebase` / 多文件搜索 | `list_files` + `search_files` | `/search` | `search` + `find` | `shell`（grep/find） |
> | 3. 源码精读 | `Read` | 打开文件 / `@file` | `read_file` | `/add` | `read` | `read_file` |
> | 4. 文本搜索 | `Grep` / `Glob` | Find in files | `search_files` | `/search` | `search` | `shell`（grep/find） |

#### 证据收集规则

- **真实读代码**，不靠猜。每条证据必须来自实际代码或配置文件。
- 边读边积累证据；**同步思考每条证据支撑哪个结论**——不支撑任何结论的证据不记录。
- 关键证据目标 3-8 条（舒适区）。超出时检查每条是否支撑独立结论——两条支撑同一点就合并。底线是每条必须支撑一个结论。
- 每条证据都标注 `文件:行号`。
- 多模块协作或 `module-overview` / `spike` 类型 → 准备一张 Mermaid 图放在速答节。
- 形成初步结论后主动检查：已有证据能否说服持怀疑态度的人？够了就停，不必扩大搜索。

为什么"够了就停"：探索不是穷举，是建立到"读者能信"为止的证据链。继续扩大只会让文档变长而不变可信。

### Phase 3：起草与确认

- **先写速答节，再回填关键证据**——先有结论再回头看证据是否真支持。这条顺序强制你检查每条证据的实际效力。
- 一次性起草完整文档。
- 起草完成后自检：对照退出条件逐项打勾。有不确定的证据或结论，在文档中明确标注（用 `<!-- 注释 -->` 或 confidence 降级）。需要用户确认的点列进后续建议，不阻塞归档。
- 有用户反馈时按反馈修订后再落盘。

### Phase 4：归档

- 写入 `docs/superpowers/explore/YYYY-MM-DD-{描述性标题}.md`
- 捕获当前 VCS 提交哈希写入 frontmatter 的 `commit` 字段（如 `git rev-parse --short HEAD`）。未提交的改动用 `HEAD`
- 若为替代：旧文档已标记 `status: outdated` + `superseded-by` 再落新文档
- 若为更新：写回原文件

### Phase 5：给出下一步建议

- 给出下一步建议（"要不要基于这份探索去设计方案"）。用户说"不用"就跳过。下一步由用户自己决定。

## 文档格式

frontmatter / 正文结构 / 各节写法说明和示例见 `references/template.md`。核心约束：

速答节是整个文档最重要的部分——大多数人只看这一节。

| 规则 | 好的 | 差的 |
|------|------|------|
| **结论前置** | "模块入口是 X，核心流程是 Y → Z" | 先列 20 行文件再给结论 |
| **可操作** | "新增 handler 加到 routes/index.ts 第 42 行" | "大概在 routes 目录里" |
| **有架构图** | module-overview/spike 附 Mermaid 图 | 纯文字描述模块关系 |
| **标注置信度** | "confidence: medium——未覆盖测试文件" | confidence: high 但只看了 2 个文件 |

## 输出语言与格式

**语言：** 报告必须使用用户正在使用的语言撰写。用户说中文就写中文，说英文就写英文。全文——包括章节标题、证据描述和结论——都跟随用户的语言。

**格式：** 默认使用 Markdown（`.md`）。用户也可以选择 HTML 格式（`.html`）。选择 HTML 时：

- 使用精致的专业样式表——不是简单的 Markdown 转 HTML。HTML 产出的视觉呈现应与 Markdown 源文件有明显区别：更丰富的排版、有意义的配色和清晰的视觉层次。
- 利用 Markdown 不具备的 HTML 能力：
  - 可折叠的 `<details>` 区域展开详细证据（保持速答节的可扫读性）
  - 颜色编码的严重程度/置信度标签（如 🔴 critical、🟡 medium、🟢 high）
  - 浮动或固定目录，方便导航
  - 样式化的提示框（`<aside>`、`<blockquote>` 变体）区分关键发现与补充说明
  - 带语法高亮和行号锚点的代码块
- 保持与 Markdown 模板相同的章节结构和内容——HTML 是展现层，不是重构层
- 内嵌 `<style>` CSS，使文档自包含、可移植（不依赖外部资源）

## 置信度标准

| 等级 | 含义 | 何时使用 |
|------|------|----------|
| **high** | 读了核心代码，结论有充分证据 | 证据 ≥ 3 条且覆盖关键路径 |
| **medium** | 读了部分代码，方向正确但细节可能有出入 | 只看了入口/接口，没深入实现 |
| **low** | 基于间接证据推测，需要进一步验证 | 只看了配置/类型定义，没看运行时逻辑 |

证据不足时 confidence **必须**降级。写 high 但只看了 2 个文件 = 欺骗读者。

## 反模式

| 反模式 | 为什么是错的 |
|--------|-------------|
| 不读代码直接给结论 | 结论是猜的，不可信 |
| 证据只写"看起来像"不写 `file:line` | 读者无法验证 |
| 结论写在证据之后 | 速答节必须在关键证据节之前 |
| 证据节比速答节长数倍 | 精简证据，不支撑结论的删掉 |
| 跨模块流程没 Mermaid 图 | 只靠文字描述无法理解流转 |
| 提前拍板 | explore 只记"看到了什么"，不下"以后应该怎么做" |
| 旧探索已过期却继续引用 | 不做标注就引用等于传播错误信息 |
| 引用旧探索但不确认 `status` | 读旧文档时先看 frontmatter 的 `status` 字段，`outdated` 文档仅作参考并标注 |

## 退出条件

在标记探索完成之前：

- [ ] 已明确探索问题与范围
- [ ] 速答节给出核心结论（结论前置）
- [ ] 关键证据 3-8 条，每条标 `file:line` 并说明支撑哪个结论
- [ ] module-overview / spike 类型的速答节有 Mermaid 图
- [ ] confidence 与证据充分程度匹配
- [ ] frontmatter 包含 `scope`（探索路径）和 `commit`（VCS 哈希）
- [ ] 文档已归档到 `docs/superpowers/explore/`
- [ ] 若为替代：旧文档已标记 `status: outdated` + `superseded-by`
- [ ] 若为更新：原文件已追加 `updated: YYYY-MM-DD`
- [ ] 已给出后续建议

## 最终规则

```
先读代码再给结论——结论必须回溯到 file:line
速答前置——读者先看结论再看证据
够了就停——证据链建立到"读者能信"为止
不拍板——explore 只记"看到了什么"
```

没有你的人类伙伴的许可，没有例外。
